# 選考履歴 migration（003）運用手順書

対象：`api-server/migrations/003_candidate_selection_events.sql`（選考履歴テーブル `public.candidate_selection_events` の作成）

- この手順書は手順の記載のみです。DB適用・Render反映は、担当者が判断して手動で行います。
- 本番DBに 003 が適用済みかどうかは確認できていません。必ず「1. 事前確認」の 3. で確認してから進めてください。
- 以下の確認SQLはすべて読み取りのみです。応募者の氏名・連絡先・理由の文面は出力しません。

## 0. 全体の順序

1. 事前確認（読み取りのみ）
2. 適用（DB）
3. 適用直後の確認（読み取りのみ）。この時点では旧コードのまま、既存画面が使えることを確認する
4. 新しいAPI・画面を Render に反映
5. 反映後の確認

DB適用と Render 反映は、どちらを先にしても既存画面は動きます。推奨はDBが先です。

- DBが先：旧コードは選考履歴テーブルを参照しないため、そのまま動きます。
- コードが先：新コードはテーブルが無い間、従来どおり動きます。選考履歴機能だけが停止し、一覧の「更新」は従来の進捗モーダルになります。

作業前に、Render で現在稼働しているコミット（切り戻し先）を記録してください。

## 1. 事前確認（読み取りのみ）

`tools/sql/selection_precheck_readonly.sql` を実行します（実行方法はファイル冒頭に記載）。

| 番号 | 確認内容 | 進めてよい条件 |
|---|---|---|
| 1・2 | `candidates.id` の型と主キー | 主キー（`p`）または一意制約（`u`）がある |
| 3 | 同名テーブル・関数 | どちらも無い（`NULL` / `false`）。有る場合は**適用しない**。既に適用済みか、失敗した旧版が残っています。構造を確認し、相談してください |
| 4 | 接続ロール・所有者・DateStyle | APIの接続ロールと所有者を記録する。DateStyle は `ISO, ...` |
| 5 | 列の型 | 面接日・内定日・入社予定日が date / timestamp。applied_at は date / timestamp / timestamptz（それ以外の場合、受付日の変更が409で停止する） |
| 6 | status と日付の組み合わせ | `NG` の件数を記録する |
| 7 | 日付の範囲外（列別） | 件数を記録する |
| 8 | 受付日・連絡履歴（409にはならない） | 件数を記録する |
| 9 | まとめ | `blocked_total` / `blocked_active` を記録する |

**409になる条件**

次のいずれかに当たる個人応募は、選考の更新（工程の追加・訂正・取消）が409で停止します。自動補正はしません。

- 6. の `NG`（status と日付の組み合わせが矛盾している、または未定義の status）
- 7. の範囲外の日付

**例外（互換扱い）：status 1（受付）＋1次面接日のみ**

対象は、2次面接日・内定日・入社予定日がない応募者です（9. の `received_with_interview_1_compatible`）。

- 409にしません。
- 既存の status（受付）と面接日はそのまま保持し、選考の画面では「1次面接（予定）・従来データ」として表示します。
- 面接日が過去でも、実施済みとは推定しません。
- 画面に確認メッセージを表示し、実施済みの場合は利用者が「1次面接（完了）」を実施日を入力して登録します。
- 一覧の表示も「受付」のままです。
- この組み合わせ以外（2次面接日・内定日・入社予定日のいずれかがある、status 2 で面接日がある等）は、従来どおり409で停止します。

`blocked_active` が0でない場合でも適用は可能です。該当する応募者は、選考の画面に「既存データと選考履歴が一致しない」と表示されます。対処（データの修正）は別途、管理者の判断で行ってください。

**運用時に409になる条件（データでは事前に判定できないもの）**

| 条件 | 409のコード |
|---|---|
| 他の画面で先に更新された | `stale` |
| 選考履歴がある応募者の管理種別（個人応募／協力業者）を変更しようとした | `coop_change_has_history` |
| 古い画面から、個人応募の選考列を保存しようとした | `selection_fields_rejected` |

## 2. 適用

- 利用の少ない時間帯に、Supabase の SQL Editor 等で 003 を**1回だけ**実行します。
- 003 は全体を1つのトランザクションで実行します。途中で失敗した場合は全体が取り消され、何も作成されません。

### タイムアウト設定（003 の冒頭で `SET LOCAL` 済み）

| 設定 | 値 | 根拠 |
|---|---|---|
| `lock_timeout` | `3s` | 外部キー作成時に candidates へ `SHARE ROW EXCLUSIVE` ロックを取ります。応募者の参照（一覧・詳細）は止めませんが、待機中は後から来た応募者の保存（PUT・選考更新）がこのロック待ちの後ろに並びます。通常の保存は数ミリ秒で終わるため、3秒取れない場合は長時間のトランザクションが残っていると判断できます。その場合は待ち続けず失敗させ、時間を置いて再実行します。**`lock_timeout` が制限するのは「ロックを取得するまでの待ち」（各ロックごとに最大3秒）だけです。** ロック取得後は COMMIT まで保持され、その間も保存は待たされます（下記「ロックの保持時間」） |
| `statement_timeout` | `60s` | 1つの文（CREATE TABLE 等）ごとの実行時間の上限です。トランザクション全体の上限ではありません。空のテーブルの作成のみのため、各文は通常1秒未満で終わります |

- `SET LOCAL` はこのトランザクション内だけ有効です。接続プールを共有する他の接続には影響しません。

**ロックの保持時間（保存が待たされる時間）**

- candidates のロックは、外部キーを作る CREATE TABLE で取得され、最後の COMMIT まで保持されます。
- 003 は人の操作を挟まずに一括で実行する前提です。その場合、保持時間は通常1秒未満です。
- 次の実行のしかたはしないでください。ロックが保持されたままになり、その間ずっと応募者の保存が止まります。
  - 003 を部分ごとに選択して実行する
  - BEGIN の後で手を止める
- 実行が終わった（成功／失敗が表示された）ことを確認してから、次の作業に移ります。失敗した場合は「4. 失敗時」の「トランザクションの終了確認」を行います。
- 3秒で失敗が続く場合は、すぐに値を延ばさないでください。先に「4. 失敗時」で待ちの原因を確認します。延ばす場合も `10s` 程度までにしてください（その間、応募者の保存が待たされます）。

## 4. 失敗時の確認・停止

**共通**

- 003 は全体が取り消されています。再実行の前に、次を確認してください（読み取りのみ）。

```sql
SELECT to_regclass('public.candidate_selection_events') AS existing_table,                     -- NULL
  EXISTS (SELECT 1 FROM pg_proc WHERE proname = 'candidate_selection_events_append_only'
    AND pronamespace = 'public'::regnamespace) AS existing_function;                           -- false
```

- 結果が `NULL` / `false` でない場合は、それ以上の操作を止めて相談してください。手作業の DROP・修正はしないでください。

**トランザクションの終了確認**

エラーの後、実行ツールによっては、失敗したトランザクションが開いたまま残ることがあります（psql の対話モードなど）。

1. **適用前に**、003 を実行する接続（同じ画面・同じセッション）で次を実行し、表示された番号（PID）を記録します。

   ```sql
   SELECT pg_backend_pid();
   ```

2. 003 が失敗したら、**同じ接続で** `ROLLBACK;` を1回実行します。
   - 取り消すだけで、何も変更しません。
   - 「トランザクションがありません」という警告が出ても問題ありません。
3. **別の接続**（別の画面・別のセッション）から、記録したPIDの状態を確認します（読み取りのみ）。

   ```sql
   SELECT pid, state, now() - xact_start AS transaction_age
   FROM pg_stat_activity
   WHERE pid = <記録したPID>;
   ```

   - 0件（接続が終了している）であれば終了済みです。
   - `state` が `idle` の場合も終了済みです。
   - `idle in transaction` / `idle in transaction (aborted)` の場合は終了していません。手順2に戻ります。

- 失敗した接続では、ROLLBACK するまで他のSQLを実行できません。そのため、確認は必ず別の接続から行います。
- Supabase の SQL Editor は実行ごとに終了します。PIDを記録しなかった場合は、別の接続から次のSQLで確認します。`idle in transaction` で残っている接続が無いことを確認してください。

  ```sql
  SELECT pid, usename, application_name, state, now() - state_change AS since
  FROM pg_stat_activity
  WHERE datname = current_database() AND (state LIKE 'idle in transaction%' OR state IS NULL);
  ```

- 確認に使う接続の条件
  - 003 を実行したのと同じロール、または他のセッションの状態を閲覧できる権限（`pg_read_all_stats` 等）を持つロールで接続します。
  - 権限が無いと、他ロールの接続の `state` は NULL になり、上の条件では判定できません。
- `state` が NULL の行がある場合、またはPIDの状態が NULL の場合は「終了を確認できない」として作業を止め、相談してください。終了したとはみなしません。
- 手順3の記録PIDの確認も、同じ条件の接続で行います。

**`canceling statement due to lock timeout`（ロック待ちで失敗）**

待ちの原因を確認します（読み取りのみ。SQL文の中身は表示しません）。

```sql
SELECT pid, usename, application_name, state, wait_event_type,
  now() - xact_start AS transaction_age
FROM pg_stat_activity
WHERE datname = current_database() AND xact_start IS NOT NULL AND pid <> pg_backend_pid()
ORDER BY xact_start;
```

- 長時間のトランザクション（`transaction_age` が長いもの）が終わるのを待ってから、時間を置いて再実行します。
- 他の接続を強制終了しないでください（`pg_terminate_backend` 等は使わない）。

**`... が既に存在します`（テーブル・関数が既にある）**

- 適用済み、または旧版が残っています。再実行・DROP はせず、構造を確認して相談してください。

**その他のエラー（外部キー・権限など）**

- エラーメッセージを記録して停止します。事前確認の 1・2・4 を見直してください。

## 6. 旧コードへ切り戻す場合（選考更新の停止手順）

**旧コードの期間中に起きること**

- 旧コードは選考履歴を知りません。個人応募の status・面接日・内定日などを、PUT で直接書き換えます。
- 旧コードは管理種別の変更時にも選考履歴を確認しません。
- そのため、旧コードの期間中の進捗変更・種別変更は、新コードに戻した後に「既存データと選考履歴が一致しない」（409）の原因になります。

**手順**

1. 利用者へ連絡する。
   - 「○時から、個人応募の進捗（選考の更新）と管理種別（個人応募／協力業者）の変更を停止します」
   - 開いている応募者の画面は閉じてもらう
2. Render で、記録しておいた切り戻し先のコミットへ戻す（手動）。
3. 旧コードの期間中の運用
   - **禁止**：個人応募の進捗変更、管理種別の変更
   - **可**：基本情報（連絡先等）の保存、協力業者の進捗更新、経費管理
   - やむを得ず進捗を変更した場合は、応募者と変更内容を記録する
4. 選考履歴テーブルは削除しない（そのまま残す）。
5. 新コードへ戻した後、次の2点を確認する。
   - 選考の画面で「一致しない」と表示される応募者を管理者が確認する。自動補正はしません
   - 次の読み取りSQLが 0 件であること（協力業者なのに選考履歴がある応募者）

```sql
SELECT count(*) AS coop_with_history
FROM public.candidates c
WHERE c.is_coop IS TRUE
  AND EXISTS (SELECT 1 FROM public.candidate_selection_events e WHERE e.candidate_id = c.id);
```

**テーブルの削除（DROP）について**

- **新コードの稼働中は削除しないでください。**
  - 新コードはテーブル有りの判定を保持しています。
  - 削除すると、応募者一覧・選考の更新・管理種別の変更がエラーになります。
- 削除してよいのは、次の3つをすべて満たす場合だけです。
  - 旧コードへ戻した後である
  - `SELECT count(*) FROM public.candidate_selection_events;` が 0 件である
  - 監査記録として残す必要がない
- 1件でも履歴がある場合は削除しないでください（監査記録が失われます）。
- 通常、切り戻しの際に削除する必要はありません。旧コードはテーブルがあっても動作します。

## 7. 完全削除（物理削除）時の選考履歴の扱い

- アーカイブ画面の「完全消去」（`DELETE /api/candidates/:id/physical`）を行うと、外部キーの連鎖削除（`ON DELETE CASCADE`）により、その応募者の選考履歴も同時に削除されます。
  - 削除される履歴には、既存データの基準値（baseline）、訂正・取消の記録、操作者が含まれます。
  - 個人情報の完全消去という機能の目的に合わせた扱いです。
- 履歴テーブルのトリガーは、この連鎖削除だけを許可します。履歴の直接の DELETE・UPDATE・TRUNCATE は拒否します。
- 削除した履歴は、アプリからは復元できません。
- 論理削除（通常の削除・アーカイブ）では、選考履歴は残ります。
- 旧コードの完全消去でも、同じく連鎖削除されます。
